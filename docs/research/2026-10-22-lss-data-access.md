# Получение персонажей LSS для расширения Foundry

Дата: 22.10.2026. Исследование публичной документации и статических ресурсов приложения. Код расширения не реализован.

## Решение

Первую версию расширения строить вокруг штатного экспорта JSON на странице «Мои персонажи». Пользователь входит в LSS обычным способом, разрешает расширению работу на этой странице и явно запускает передачу экспорта в подключённую вкладку Foundry. Расширение получает файл в памяти, позволяет выбрать персонажей и передаёт исходные документы существующему импортёру модуля.

OAuth не является обязательной предпосылкой этого сценария. Он понадобится для другого UX: самостоятельного получения списка персонажей из фонового процесса расширения, без открытой страницы LSS. Предыдущий вывод в `extension-design.md` о полном блокировании расширения до появления API был слишком широким: он применим к такому самостоятельному API-клиенту, но не к переносу штатного экспорта.

## Подтверждённые факты

### 1. Есть экспорт одного персонажа и списка

В публичном чанке [4913-3731714bbdb0c87a640a.js](https://longstoryshort.app/4913-3731714bbdb0c87a640a.js) обнаружены:

- Пункт «Скачать .json» в меню одного персонажа: обработчик `pe(e)` передаёт `re(te.raw[e])` функции `ve`.
- Кнопка «Скачать .json» для списка: `ve(re(te.raw), "Мои персонажи")`. Передаётся текущая коллекция `te.raw`; она зависит от фильтров списка, поэтому нельзя обещать экспорт всего аккаунта при включённых фильтрах.
- `re` удаляет `_id`, `playerId`, `createdAt`, `updatedAt`, `__v`, добавляет `jsonType = "character"` и `version = "2"`.
- `ve` кодирует JSON в `data:application/json;charset=utf-8,` и создаёт `<a download>`, добавляет ссылку в DOM, вызывает `click()`, удаляет ссылку.

Это подтверждение по клиентскому коду от 22.10.2026. Экспорт под аккаунтом в ходе исследования не запускался.

Следствие: расширению не нужно извлекать токен или разбирать React state. Можно получить тот же JSON, который сайт предназначает для скачивания. Формат конверта описан в [документации персонажа](https://longstoryshort.app/doc/developers/characters/).

### 2. Доступ по ссылке существует

В публичном чанке [30cd56ec8b4292fd1d19f6bfd4b67b1689d06305-20fa6ba5da81f350e7a5.js](https://longstoryshort.app/30cd56ec8b4292fd1d19f6bfd4b67b1689d06305-20fa6ba5da81f350e7a5.js) обнаружены:

- Переключатель «Доступ по ссылке (просмотр)» с пояснением «Лист смогут смотреть все, у кого есть ссылка».
- Переключение `linkAccess` между `view` и `none`; клиент использует `PATCH /character/:id/link-access/`.
- Ссылка листа строится как `/characters/builder/:id/` либо `/characters/digital/:id/`.
- Отдельные личные разрешения: `accessLevel: view | edit` и `userId`.

Не подтверждено: позволяет ли сервер читать открытый по ссылке JSON вообще без аккаунта; что именно возвращает для гостя и для пользователя с правом просмотра; доступность гримуара владельца. Переключатель просмотра сам по себе не является контрактом анонимного API.

Для своих персонажей открывать доступ по ссылке не требуется. Для чужого персонажа это возможный механизм выдачи прав, но его нужно отдельно проверить на специально предоставленном тестовом листе. Настройки прав расширение не меняет автоматически.

### 3. Внутренние методы чтения видны, публичного контракта нет

В [aa728e634c79773f1684bf6fdc659cc94c0382a5-62c6f1fbe6974f375d43.js](https://longstoryshort.app/aa728e634c79773f1684bf6fdc659cc94c0382a5-62c6f1fbe6974f375d43.js) и чанке списка найдены:

- `GET /character/list/` — список персонажей.
- `GET /character/:id/` — персонаж; ответ используется для `data`, `edition`, `sheetEdition`, `spells`, `disabledBlocks`, `access`, `linkAccess`.
- `GET /spells/custom/` — собственные заклинания.
- `GET /spells/list/?ids=...&full=true&description=true&edition=...` — получение заклинаний.
- API-хост `https://api.longstoryshort.app`, передача `Authorization: Bearer ...`. Общий helper при отсутствии JWT и специального флага не делает запрос; поведение сервера без JWT из этого не следует.

`GET /character/:id` также прямо упомянут в [разделе «Живой экспорт vs генератор с нуля»](https://longstoryshort.app/doc/developers/characters/#живой-экспорт-vs-генератор-с-нуля). Но найденная документация не задаёт для стороннего клиента авторизацию, разрешения, пагинацию и стабильность этих маршрутов. Методы здесь только описаны; запросы к ним не выполнялись.

### 4. OAuth существует, но свой клиент ещё не зарегистрирован

В [публичном чанке страницы согласия](https://longstoryshort.app/component---src-pages-oauth-authorize-tsx-74fc3e20bfca205dee2a.js) обнаружены `client_id`, `redirect_uri`, `scope`, `code_challenge`, `state`, показ имени приложения и серверная проверка запроса. Это подтверждает механизм согласия, но не возможность самостоятельно зарегистрировать наше приложение и не наличие scopes чтения персонажей. Чужой `client_id` не использовать. Для самостоятельного API-клиента согласовать эти параметры с LSS.

### 5. SDK решает другую задачу

Проверен репозиторий `tldrpg/lss-vtt-sdk`, commit `0827cbfad416d5dcd1b6874b0ea15d16f65acf7a`: [src/types.ts](https://github.com/tldrpg/lss-vtt-sdk/blob/0827cbfad416d5dcd1b6874b0ea15d16f65acf7a/src/types.ts).

`CapabilityManifest` содержит систему и список разрешённых операций; `HealthChangedPayload` — id персонажа и HP. В `SheetEvent` нет экспорта полного персонажа, списка аккаунта или гримуара. Снапшот из справочника SDK означает повтор последнего события состояния, а не выдачу полного JSON листа.

[Встраивание](https://longstoryshort.app/doc/developers/embedding/) требует разрешённого рабочего домена; `localhost` в список не добавляется. [Группы](https://longstoryshort.app/doc/developers/embedding/groups/) дают участникам чтение подключённых листов, но не добавляют SDK-метод экспорта JSON. Встраивание можно рассматривать отдельно для бросков и HP, а не как замену импорту Actor/Item.

### 6. Гримуар экспортируется отдельно

[Документация Гримуара](https://longstoryshort.app/doc/spells/addition/) описывает «.json» → «Скачать .json». Полный формат этого экспорта и способ его получения в DOM не проверены. В персонаже лежат ссылки на заклинания, поэтому нельзя обещать перенос описаний своих заклинаний по одному JSON персонажа. Первая версия должна принимать отдельный экспорт Гримуара; автоматический захват этого экспорта проверяется отдельно.

## Сравнение вариантов

| Подход | Преимущества | Ограничения | Выбор |
|---|---|---|---|
| Штатный экспорт в открытой LSS-вкладке | Есть один и несколько персонажей; не нужен токен расширения; работает с текущим импортёром | Нужен явный экспорт; DOM сайта может измениться | Первая версия |
| JSON по ссылке | Удобно импортировать конкретного расшаренного персонажа | Не подтверждены анонимное чтение и контракт API; нет списка аккаунта | Отдельный проверяемый адаптер позже |
| Собственный OAuth + API | Прямой выбор персонажей из окна Foundry, фоновые запросы | Требуются зарегистрированный клиент и согласованный контракт | Долгосрочная интеграция |
| SDK/iframe | Официальный транспорт бросков и HP | Нет полного JSON; ограничения доменов | Не использовать для переноса персонажа |

## Предлагаемый первый сценарий

1. Пользователь подключает конкретный адрес Foundry в popup расширения.
2. На открытой странице «Мои персонажи» нажимает в расширении «Передать следующий экспорт в Foundry».
3. Сам выбирает штатный экспорт одного персонажа или списка в LSS.
4. Content script в течение ограниченного времени принимает только ожидаемую ссылку `data:application/json` с `download` и корректным документом персонажа. Перехват сгенерированного клика в capture-фазе можно использовать, чтобы предотвратить скачивание; это нужно подтвердить браузерным прототипом. Сохранение файла не должно зависеть от непроверенной возможности подавить скачивание.
5. Расширение показывает выбор полученных персонажей и целевую вкладку; модуль Foundry открывает предпросмотр импорта с обычным подтверждением пользователя.
6. Гримуар пользователь добавляет отдельным JSON. После проверки экспортного механизма Гримуара можно добавить аналогичную передачу.

Логика аутентификации и запросов остаётся у LSS. Расширение не получает пароль/JWT, не читает хранилища авторизации, не вызывает внутренние маршруты и не собирает цифры из отрисованного листа. Content script передаёт только выбранный экспорт, background проверяет источник и подключённый origin Foundry, модуль повторно валидирует документ и права пользователя. Размер документов и срок ожидания ограничиваются. Весь трафик персонажей идёт внутри браузера, сторонний сервер не требуется.

Официальный экспорт удаляет id персонажа: первая версия создаёт новых актёров, как текущий модуль. Надёжное обновление существующего Actor требует отдельного решения об идентичности, а не сопоставления только по имени.

## Проверки перед реализацией и готовность

- На реальном браузере подтвердить захват экспорта одного персонажа и списка, включая фильтры, кириллицу и отмену операции. До этого описанный механизм — проектное решение по исходникам, а не проверенная интеграция.
- Отдельно проверить экспорт Гримуара и формат данных.
- С пользовательской тестовой ссылкой проверить доступ: владелец, другой вошедший пользователь, гость; выключенный/включённый `linkAccess`. Не проверять чужие случайные id и не менять права автоматически.
- Для OAuth уточнить регистрацию клиента, redirect URI, read-only scopes и контракт API. Для первого сценария это не блокер.
- Контекст проекта запрещает в ходе исследования входить в LSS и обращаться к непубличным endpoint; эти действия не выполнялись. Код загруженных скриптов не исполнялся. Foundry не запускалась, пользовательские данные не менялись.

Проверены документация Guildhall и публичные клиентские ресурсы, относящиеся к этим механизмам; локальный HEAD совпадает с удалённым `master`: `3db6a0c7bbe539ecd0a832e7164d482384d6fb49`. Изменения сторонних рабочих файлов Guildhall не затрагивались. Независимый аудит через Claude недоступен: OAuth-сессия Claude истекла, стоимость вызова $0, токены 0; выводы получены непосредственным чтением источников.
